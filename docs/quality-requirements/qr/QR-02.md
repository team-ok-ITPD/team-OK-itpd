# QR-02: Learner Code Stays Inside Its Own Workspace

A program a learner runs cannot read another learner's files or the host's files, and one that runs away is stopped without affecting other learners.

- **Status:** Active
- **Characteristic:** Security
- **Sub-characteristic:** Resistance
- **Business importance:** High
- **Technical risk:** High

## Scenario

### Source

A learner, or a program a learner runs, that tries to reach beyond its own exercise.

### Stimulus

The program tries to read files outside its own workspace, or uses more CPU, memory or processes than its allowance, such as an endless loop or a runaway process.

### Environment

Several learners use the product at the same time on one shared service, as in the pilot of [`TOS-01`](../../threshold-of-success.md#tos-01) and [`RISK-03`](../../risks.md#risk-03), with five learners at once.

### Artifact

The prepared workspace each learner gets, and the shared service that hosts it.

### Response

The program shall be unable to read or change anything outside its own workspace, and a program that exceeds its allowance shall be stopped, while the other learners' workspaces keep working.

### Response Measure

In a test with five workspaces running at once, a hostile test program reads zero files outside its own workspace, a runaway process is stopped within 30 seconds, and the other four workspaces still answer their health check within two seconds throughout.

This scenario is for a future shared deployment. The current learner-local Compose service does not implement five-user provisioning, authentication or resource enforcement. Zero access outside the workspace concerns protected host and other-learner data, not the runtime files required to execute Python.
