# QR-03: The Product Checks Run From A Clean Checkout

A developer can run the product's checks from a clean checkout with one documented command, and a broken change to a critical module makes them fail.

- **Status:** Active
- **Characteristic:** Maintainability
- **Sub-characteristic:** Testability
- **Business importance:** High
- **Technical risk:** Medium

## Scenario

### Source

A team member, or the continuous integration run, with a fresh clone of the repository.

### Stimulus

The member installs the pinned dependencies and runs the documented check command after changing a critical module.

### Environment

A clean checkout with the dependencies of `requirements.lock` installed and no other local setup, on the Python version the product container uses.

### Artifact

The critical modules, which are the frontend entry point `app/static/app.js`, the catalog backend `app/server.py` with its workspace readiness check, and the exercise and its reference solution, `exercise/remove_negatives.py` and `exercise_author/correct_remove_negatives.py`.

### Response

The checks shall run to the end without further setup, report which module failed, and fail when a critical module's behavior is broken.

### Response Measure

`python -m pytest` run from the repository root exits with status 0 in under 60 seconds on the unchanged repository, and exits with a non-zero status for a deliberate behavior-breaking change in each of the four critical modules.

The baseline Python suite verifies the catalog and exercise contract but does not detect a broken frontend entry point. This measure remains an acceptance target; a passing pytest run is not evidence of complete critical-module coverage.
