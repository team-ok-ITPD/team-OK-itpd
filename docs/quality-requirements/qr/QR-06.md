# QR-06: An Operator Can Diagnose A Failed Request

An operator who is told a catalog search failed can find that request and read its latency in the staging organization within minutes, without access to the host.

- **Status:** Active
- **Characteristic:** Maintainability
- **Sub-characteristic:** Analysability
- **Business importance:** High
- **Technical risk:** Medium

## Scenario

### Source

A system operator who has been told that a learner's catalog search failed.

### Stimulus

A search request in the core task fails with an error response.

### Environment

The product runs on the staging deployment and sends its signals to the staging organization of the observability backend, as described in [ADR-005](../../architecture/adr/ADR-005.md).

### Artifact

The catalog's request log line and the request-duration metric defined by [SLI-01](../../observability.md#sli-01), and the backend that stores them.

### Response

The operator shall find the failed request by its request identifier and read its route and failure label, and shall read the failure series of the duration metric.

### Response Measure

Within five seconds of the failed request's response, a query of the staging organization returns one log point for it, carrying its request identifier, route and failure label. Within one minute, the query of SLI-01 returns the failure series with a P95 value.

The scenario concerns the product's signals, not the dashboard. The numerical targets remain proposals for Customer review.

## QRT-01

A failed search on the staging deployment is found in the staging organization by its request identifier within five seconds, and the failure series of SLI-01 has a numeric P95 within one minute.

- **Status:** Active
- **Level:** deployed
- **Runs at:** the staging deployment at `$STAGING_URL`, queried through the staging organization at `$OPENOBSERVE_URL`, reading [SLI-01](../../observability.md#sli-01), from a machine on the university network.

### Procedure

1. Set `STAGING_URL`, `OPENOBSERVE_URL`, the staging organization name and the credentials in the environment; the credentials are not committed.
2. Run `python scripts/check_sli.py`. It signs in, sends one search that succeeds and one that fails with a 404, and keeps the `X-Request-ID` of the failed response.
3. The script queries the staging organization for the log point with that request identifier, waiting up to five seconds, and prints its `request_id`, `route`, `outcome`, `status` and `duration_ms`.
4. The script runs the SLI-01 query and waits up to one minute for a numeric P95 in the `client_error` series, then prints it.
5. Record the printed output, the dashboard screenshot, the staging environment and the commit the test ran against.

**Pass when:** the log query returns exactly one point for the failed request with its request identifier, route and failure label within five seconds, and the SLI-01 query returns a numeric P95 for the `client_error` series within one minute.
