# ADR-004: Verify Submissions In Fresh Containers

- **Status:** Accepted
- **Created:** 2026-11-08
- **Updated:** 2026-11-08
- **Containers:** `exercise catalog`, `debug workspace`
- **Addresses:** [`FR-011`](../../functional-requirements/fr/FR-011.md), [`QR-02`](../../quality-requirements/qr/QR-02.md)
- **Decision:** [`DEC-037`](../../decisions.md#dec-037)

## Context

Submitted code is untrusted and decides a learner's recorded result. Counts sent by a browser or the VS Code extension can be forged, and running the code inside the catalog process would expose the host and other learners.

## Considered Options

- Trust the client's reported counts: rejected because any client can claim success.
- Run tests inside the catalog process: rejected because runaway or hostile code would affect the service and other learners.
- Run each submission once in a fresh, resource-limited container: chosen.

## Decision Outcome

The catalog starts a short-lived Docker container per submission with no network and limits on memory, CPU, processes and run time, reads the test result, and removes the container. A bounded gate limits concurrent runs and the waiting queue. This describes the existing implementation in `app/adel_b/bugs/verification.py`; shared-service isolation beyond this remains unvalidated ([RISK-03](../../risks.md#risk-03)).

## Consequences

- Recorded results come from the server, supporting [QR-02](../../quality-requirements/qr/QR-02.md) resistance.
- Each submission pays container start-up time and needs Docker access from the catalog.
- Under load, extra submissions are refused as busy instead of degrading everyone.
