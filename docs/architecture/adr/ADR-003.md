# ADR-003: Isolate Each Learner Workspace And Bound Learner-Code Execution

- **Status:** Accepted
- **Date:** 2026-10-24
- **Decision makers:** Debug GYM team
- **Requirements:** [FR-002](../../functional-requirements/fr/FR-002.md), [FR-005](../../functional-requirements/fr/FR-005.md), [QR-02](../../quality-requirements/qr/QR-02.md), [QR-04](../../quality-requirements/qr/QR-04.md)
- **Quality attributes:** [QR-02: Security / Resistance](../../quality-requirements/qr/QR-02.md), [QR-04: Performance Efficiency / Time Behaviour](../../quality-requirements/qr/QR-04.md)

## Context

Learners execute editable code, tests, and debugger processes. In a shared service, unrestricted execution could expose another learner's files or host resources, as [RISK-03](../../risks.md#risk-03) records. The current minimum usable product is learner-local and does not yet implement or validate the shared-service controls in this decision.

## Decision Drivers

- [FR-002](../../functional-requirements/fr/FR-002.md) requires an independently ready workspace and cleanup after preparation failure.
- [FR-005](../../functional-requirements/fr/FR-005.md) requires valid-access admission and refusal of invalid access.
- [QR-02](../../quality-requirements/qr/QR-02.md) requires filesystem and resource isolation for five concurrent learners.
- [QR-04](../../quality-requirements/qr/QR-04.md) requires an available workspace within 30 seconds.

## Considered Options

- Give each learner an isolated workspace and store with bounded resources and authenticated routing.
- Run all learners in one shared workspace and process boundary.
- Execute learner code directly on the service host.
- Depend only on application-level path validation.
- Keep learner-local execution as the permanent deployment model.

## Decision

Before a shared or public deployment, give each learner a separate `debug workspace` and `workspace store`. Do not share writable files or execution processes between learners. Do not expose host files or unrestricted host resources. Apply CPU, memory, process, and execution-time limits, and admit and route only the authenticated learner to each workspace, including its remote SSH endpoint required by FR-005.

Continue learner-local deployment as the contingency until the shared design passes QR-02. Acceptance of this target architecture does not claim that the current MUP already implements its controls.

## Consequences

### Positive

- Filesystem and process boundaries directly address the shared-service threat in RISK-03.
- Per-workspace limits allow runaway learner code to be stopped without stopping other workspaces.
- Authenticated routing supplies a clear boundary for the access behavior in FR-005.

### Negative

- Provisioning, authentication, routing, and resource enforcement add operational work not present in the current MUP.
- Separate workspaces consume more resources than a shared process.
- The team must validate isolation and startup time together before a public pilot.

## Rejected Alternatives

### One Shared Workspace And Process Boundary

A learner could affect another learner's files or execution, directly violating QR-02.

### Execute Learner Code On The Service Host

Host execution exposes infrastructure to editable learner code and provides no adequate containment boundary.

### Application-Level Path Validation Only

Path checks do not bound CPU, memory, process creation, or debugger execution and therefore cover only part of QR-02.

### Learner-Local Execution As The Permanent Model

Local execution is the safe contingency, but by itself it cannot demonstrate the five-learner shared-service scenario in QR-02.
