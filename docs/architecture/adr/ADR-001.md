# ADR-001: Adopt The Docker, code-server, Python, And pytest Stack And Split Responsibilities

- **Status:** Accepted
- **Date:** 2026-10-24
- **Decision makers:** Debug GYM team
- **Requirements:** [FR-001](../../functional-requirements/fr/FR-001.md), [FR-002](../../functional-requirements/fr/FR-002.md), [FR-003](../../functional-requirements/fr/FR-003.md), [FR-004](../../functional-requirements/fr/FR-004.md), [FR-005](../../functional-requirements/fr/FR-005.md), [QR-03](../../quality-requirements/qr/QR-03.md), [QR-04](../../quality-requirements/qr/QR-04.md), [QR-05](../../quality-requirements/qr/QR-05.md)
- **Quality attributes:** [QR-03: Maintainability / Testability](../../quality-requirements/qr/QR-03.md), [QR-04: Performance Efficiency / Time Behaviour](../../quality-requirements/qr/QR-04.md), [QR-05: Reliability / Recoverability](../../quality-requirements/qr/QR-05.md)

## Context

The product must provide a prepared Python exercise, VS Code debugging tools, repeatable pytest checks, and recoverable learner files. The Week 2 spike and [DEC-005](../../decisions.md#dec-005) established Docker, code-server, Python, and pytest as a viable minimum stack. The architecture still needs explicit ownership boundaries even though the minimum usable product packages its applications in one image and Docker Compose service.

## Decision Drivers

- [FR-001](../../functional-requirements/fr/FR-001.md) and [FR-002](../../functional-requirements/fr/FR-002.md) require exercise matching and a ready workspace.
- [FR-003](../../functional-requirements/fr/FR-003.md) and [FR-004](../../functional-requirements/fr/FR-004.md) require pytest in the workspace, while [FR-005](../../functional-requirements/fr/FR-005.md) requires authenticated remote SSH access to its VS Code debugger.
- [QR-03](../../quality-requirements/qr/QR-03.md) requires automated checks from a clean checkout.
- [QR-04](../../quality-requirements/qr/QR-04.md) sets response-time targets for opening the exercise.
- [QR-05](../../quality-requirements/qr/QR-05.md) requires a repeatable reset path.

## Considered Options

- Docker with code-server, Python, and pytest, split into explicit logical responsibilities.
- Install all tools directly on each learner's host.
- Keep one undifferentiated application responsibility.
- Use an externally hosted IDE and workspace service.

## Decision

Use a learner-local Docker deployment with code-server, Python, pytest, and debugpy. Split responsibilities across the three containers in the container view:

- `exercise catalog` owns request matching, catalog metadata, and workspace-readiness checks.
- `debug workspace` owns code-server, Python and pytest execution, and the running editor and debugger session. A target deployment that preserves FR-005 also exposes this workspace to VS Code through authenticated remote SSH.
- `workspace store` owns persistent exercise files and editor configuration.

The logical split remains authoritative while the current minimum usable product deploys the `exercise catalog` and `debug workspace` in one image and Compose service.
Its unauthenticated browser-only access does not satisfy FR-005; remote SSH and access refusal remain target capabilities unless the Customer changes that requirement.

## Consequences

### Positive

- The selected stack reuses the proven spike and supports the required Python and VS Code workflow.
- Named responsibilities make later deployment changes possible without changing the required behavior.
- The persistent store gives reset and recovery a defined data boundary.

### Negative

- The current single-image packaging couples catalog and workspace releases.
- Authenticated remote SSH still has to be implemented and tested before FR-005 can pass.
- A clean start depends on Docker image, package, and extension availability described by [RISK-02](../../risks.md#risk-02).
- Resetting the named volume deliberately discards learner changes.

## Rejected Alternatives

### Install Tools Directly On The Learner Host

This makes environment preparation depend on each learner's machine and conflicts with the ready-workspace behavior in FR-002.

### One Undifferentiated Application Responsibility

This hides ownership of catalog state, execution state, and persistent files and makes independent evolution harder to verify.

### Externally Hosted IDE And Workspace

This adds a provider dependency before the team has validated the minimum learner-local workflow and its quality targets.
